方案日期：2026-07-19。

当前状态：批次 0～6 已完成；批次 7 待实施。

本文是《Android 端代码审核报告》的配套实施方案，也是本轮整改进度的唯一明细状态源。后续执行者必须按批次更新本文进度表、实施记录和根目录 `ROADMAP.md`。

## 1. 目标与成功标准

### 1.1 目标

1. 建立不可由普通账号绕过的模块、用户管理和数据访问权限边界。
2. 删除默认员工账号和明文密码写入，统一密码生成、验证和历史升级；保留唯一默认账号 `admin / 123456`。
3. 修复编辑用户清空密码、失败仍提示成功等确定性逻辑错误。
4. 保证采购明细与汇总、患者及关联数据的变化具有原子性和一致业务语义。
5. 配置损坏时不删除原配置、不静默切换数据源。
6. 让同步表配置与实际执行范围一致。
7. 收口会话状态，避免退出后保留旧用户和权限缓存。
8. 增量治理严重硬编码，不开展与问题无关的全仓视觉重构。

### 1.2 最终成功标准

- 普通用户不能进入用户管理、设置或未授权模块，也不能通过 Provider／Service 直接执行未授权写入。
- 身份、医生字段或权限配置缺失时失败关闭，不返回全量医疗或财务数据。
- 新密码统一使用带随机盐的慢哈希格式；旧 MD5、SHA-256 和明确历史明文只在兼容验证中出现，并在成功登录后升级。
- 新安装只创建一个默认账号 `admin / 123456`；密码经统一密码服务哈希保存，且不能验证其他账户。
- 编辑用户留空密码不会修改密码列；所有新增、编辑、删除提示与数据库真实结果一致。
- 采购明细和汇总在同一事务中提交；断线重试不会重复插入。
- 患者删除在 SQLite 与 MySQL 中使用相同的禁止、级联或软删除语义，不产生部分删除或孤儿数据。
- 配置读取失败保留原文件并明确阻止静默降级；配置写入具备原子替换。
- 同步执行严格使用已保存的表范围，并有顺序、外键和整表覆盖测试。
- 登录、退出和数据库切换只维护一个当前用户真源。
- 所有规定的自动测试、静态检查和人工回归完成后，批次才能标记为已完成。

## 2. 实施原则与红线

### 2.1 必须遵守

- Bug 修复先建立失败测试或等价可重复复现，再修改代码。
- 每个批次只解决本文列出的目标，不顺手清理无关代码或格式化全仓。
- SQLite 与 MySQL 行为必须同时设计；无法自动覆盖 MySQL 时必须列出人工验证步骤。
- 权限检查至少覆盖页面／路由与应用服务两层；数据范围必须落实到查询层。
- 密码、数据库凭证、患者手机号和身份证号不得写入日志。
- 事务闭包内不得混入不可回滚的文件、偏好或外部副作用。
- 所有新增配置值、角色、权限键、视觉 token 和业务默认值集中管理。

### 2.2 必须先向主人确认的事项

以下事项命中项目红线或会改变产品行为，不能在执行时自行决定：

1. 删除或迁移已有数据库中的 `admin`／`staff` 账号数据；删除新数据库的默认 `staff` 创建逻辑已由主人确认，不属于此处的数据迁移。
2. 采用数据库 schema 变更、软删除字段或数据迁移。
3. 修改 `AndroidManifest.xml`、原生权限、网络安全配置或 Gradle 配置。
4. 删除文件、目录或执行 Git 回滚。
5. 任何生产部署、发布、远端数据库操作或公开发布。

### 2.3 不在本轮范围

- 不做全仓主题换肤或一次性拆分所有大文件。
- 不因为本轮审核顺手升级依赖。
- 不修改 Windows 端对应实现。
- 不在未确认产品规则前自行决定普通用户能查看哪些医生的数据。

## 6. 批次 1：认证测试与统一密码服务

### 6.1 设计决策

优先使用现有 `crypto` 依赖实现版本化 PBKDF2-HMAC-SHA256，避免新增依赖。存储格式应自描述，例如：

```text
pbkdf2_sha256$<iterations>$<base64_salt>$<base64_hash>
```

迭代次数集中定义；每个密码使用 `Random.secure()` 生成独立盐；比较使用常量时间方式。

兼容验证只允许：

1. 新 PBKDF2 格式。
2. 历史 64 位十六进制 SHA-256。
3. 历史 32 位十六进制 MD5。
4. 经审核确认确实存在的历史明文值。

历史格式验证成功后升级到新格式。任何格式判断、明文兼容和升级写回都只能存在于密码／认证服务，不能散落在 Widget、Provider 和 DataSource。

### 6.2 测试先行

新增测试至少覆盖：

- 同一密码两次生成不同存储值，但都能验证成功。
- 错误密码失败。
- 畸形格式、非法 Base64、非法迭代次数安全失败。
- 历史 MD5、SHA-256 和明确明文正确验证，并标记需要升级。
- `123456` 不能登录密码不是 `123456` 的任意账户。
- 升级写回失败不会输出原始密码。
- SQLite 与 MySQL 认证服务使用相同验证结果语义。

### 6.3 实施步骤

1. 新增单一 `PasswordService`，集中生成、验证、格式识别和升级判断。
2. 将 User CRUD、默认管理员和密码更新入口改为调用该服务。
3. DataSource 只负责按用户名读取用户和按 ID 更新密码，不再自行计算哈希。
4. 认证日志移除原始密码、完整哈希和数据库密码。
5. 保留受限历史兼容；不再新增 MD5、SHA-256 或明文写入。
6. “记住密码”继续使用现有本地应用存储方式，不新增远端凭证服务、系统级凭证管理器或迁移流程。

### 6.4 验收

- 所有新密码只有一种版本化格式。
- 旧格式可以按规则登录并升级。
- 不存在固定密码绕过和敏感日志。
- 密码测试、全量测试和静态检查通过。

### 6.5 实施记录

- 2026-07-20：新增 `PasswordService`，新密码统一保存为 PBKDF2-HMAC-SHA256；SQLite、MySQL 数据源只负责读取用户及按 ID 更新密码。历史 SHA-256、MD5 和明文验证成功后升级；认证、哈希日志均不再输出原始密码或完整哈希。新增密码专项 4 项测试，覆盖随机盐、错误密码、畸形格式、历史格式及固定密码不能跨账户认证。

## 9. 批次 4：会话唯一真源

### 9.1 设计决策

推荐由单一 `SessionProvider` 或收口后的 `UserProvider` 保存当前用户、登录状态和权限缓存。`AppState` 不再单独保存另一份用户对象。

### 9.2 测试先行

- 登录成功后所有消费者读取同一个用户实例／快照。
- 退出登录后当前用户、权限缓存和医生过滤立即清空。
- 退出到登录页期间后台加载不能继续使用旧身份。
- A 用户退出后 B 用户登录，不复用 A 的权限和业务缓存。
- 数据源切换后会话采用明确的保留、重新认证或退出策略。

### 9.3 实施步骤

## 10. 批次 5：采购事务与患者删除一致性

### 10.1 采购设计

采购明细新增、编辑、删除与主记录汇总更新必须构成一个事务用例：

```text
开始事务
  写入明细
  在同一事务中重新计算汇总
  更新主记录
提交事务
```

SQLite 使用 `Database.transaction`；MySQL 使用连接事务 API。重试边界放在事务外，只重试确认未提交的事务。新增操作增加业务幂等键或等价重复保护。

### 10.2 患者删除产品决策

主人于 2026-07-20 确认：患者删除保持现有“删除全部关联数据”行为，本批次不修改患者删除代码、不新增 schema 或迁移。后续如要改为禁止删除、软删除或调整关联范围，必须重新确认。

### 10.3 测试先行

- 采购明细写入成功但汇总失败时，整个事务回滚。
- 模拟连接错误重试后只有一条明细。
- 更新、删除后明细和主记录汇总始终一致。
- 患者有关联预约、财务、材料、病历和图片时符合选定策略。
- 任一关联处理失败时不产生部分删除。
- 删除不存在记录返回失败，UI 不显示成功。

### 10.4 实施步骤

1. 将采购复合写入移入 DataSource 或专用事务 Service，Provider 只编排结果和缓存。
2. 收窄 `DatabaseOperationWrapper`：禁止自动重放非幂等闭包，或要求调用者显式声明幂等性。
3. 实现患者关联数据清单和统一删除／禁止策略。

5. 只有事务提交后清除缓存和通知 UI。
6. 页面严格检查结果并展示可理解错误。

### 10.5 验收
