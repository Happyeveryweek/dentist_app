# Android 端代码审核报告

审核日期：2026-07-19。

审核状态：已完成只读审核；本文仅记录问题、证据、影响和整改优先级，不代表问题已经修复。

## 1. 审核结论

Android 端当前能够通过 Flutter 静态检查，但仍存在静态分析无法识别的认证、授权、数据一致性和架构安全问题。本轮确认的主要问题包括：

- 3 项严重问题：登录后的权限边界失效、内置固定管理员弱密码、用户编辑会意外重置密码并误报成功。
- 4 项高风险问题：密码存储与升级规则分裂、采购复合写入可能因重试产生重复数据、患者删除流程不完整、数据库配置异常时静默删除并切换数据源。
- 4 项中风险或系统性规范问题：同步表配置不生效、会话状态存在双数据源、原生权限与明文网络范围过大、视觉和业务默认值硬编码严重。

综合判断：产品已明确只在受控诊所局域网内使用，直连 MySQL、现有网络／原生权限和本地密码持久化不纳入本轮整改。权限、密码业务逻辑和数据事务问题仍需优先修复。

## 2. 审核范围与方法

### 2.1 范围

- `android_app/lib/` 下 272 个 Dart 文件。
- `android_app/android/app/src/main/AndroidManifest.xml` 与网络安全配置。
- 用户认证、权限、患者、采购、同步、数据库配置和 Provider 初始化主链路。
- `android_app/pubspec.yaml` 中与数据库、安全存储和文件访问有关的依赖。
- 根目录 `ROADMAP.md` 与 Android 子项目既有治理结论。

本轮未审核 Windows 端业务实现，也未改动任何业务代码。

### 2.2 方法

1. 阅读根目录和 Android 子项目规则、当前 Roadmap 和既有治理总结。
2. 检索密码、默认账号、角色、权限、数据库连接、配置持久化、SQL、异步状态和硬编码模式。
3. 沿现用调用链核对 UI、Provider、Service 与 DataSource，避免只按单个代码片段判断。
4. 检查跨表、明细与汇总写入是否具有事务和幂等保护。
5. 执行 Flutter 静态检查确认当前基线。

### 2.3 基线验证

在 `android_app/` 执行：

```bash
cmd.exe /c flutter analyze
```

结果：`No issues found!`，运行时间 22.7 秒。

该结果只说明 analyzer 未发现类型、语法和 lint 问题，不能证明权限、密码、事务和错误结果处理正确。

## 3. 严重问题

### P0-1：登录后没有形成有效的模块和账号管理权限边界

#### 证据

- `lib/screens/home_screen.dart` 只检查 `AppState.isLoggedIn`，随后向所有登录用户提供患者、预约、业务和设置入口。
- 同文件的业务管理页固定创建财务、采购、用户三个子页面，没有按 `module_permissions` 或角色过滤。
- `lib/screens/users_screen.dart` 的新增、编辑、删除按钮不经过 `PermissionWrapper` 或管理员判断。
- `UserProvider.addUser`、`updateUser`、`deleteUser` 和 `updateUserPermissions` 等写入口不接收操作者上下文，也没有服务层授权检查。
- `lib/features/users/services/user_permission_service.dart` 的 `shouldFilterByDoctor()` 固定返回 `false`，并明确说明 Android 端所有用户都能查看所有数据。

#### 实际影响

- 普通登录用户可以进入用户管理，创建管理员、修改其他账号角色或密码、删除账号。
- 普通用户可以进入设置和业务模块，即使其 `module_permissions` 对应值为 `false`。
- UI 层部分按钮的权限包装不能保护 Provider 和 DataSource 写入口，后续新增入口时很容易绕过。
- 患者、财务、采购和预约的数据可见范围与已有权限模型不一致。

#### 根因

权限目前主要作为局部 UI 交互能力存在，没有成为路由、页面、应用服务和数据库查询共同遵守的业务边界；模块权限和医生数据范围也混在同一个布尔判断体系中。

#### 目标

- 未授权模块不能进入或加载数据。
- 用户管理仅管理员可访问和写入。
- Provider／Service 写入口必须再次校验权限，不能只依赖按钮隐藏。
- 数据可见范围按明确产品规则处理；身份缺失时失败关闭，不能返回全量数据。

### P0-2：新数据库内置明文默认账号，并额外创建无必要员工账号

#### 证据

`lib/models/database_models.dart` 在用户表为空时直接插入：

- 管理员：`admin / 123456`，密码明文保存。
- 员工：`staff / 123456`，密码明文保存。
- 日志直接输出上述账号密码。

`staff` 角色还不在当前用户编辑界面支持的 `user`、`doctor`、`admin` 角色集合内，角色定义本身不一致。

#### 实际影响

- 新安装实例具有公开、可预测的管理员初始凭证，必须明确限制其用途和风险边界。
- 明文密码会在首次成功登录前持续保存在数据库中。
- 默认员工角色可能被后续角色修复逻辑改写，产生不可预期的权限变化。

#### 已确认产品决定

主人于 2026-07-19 确认：

- 删除默认 `staff / 123456` 的创建逻辑。
- 新安装只保留一个默认账号 `admin / 123456`。
- `123456` 只能验证默认 admin 自身保存的密码，不能作为登录任意账户的通用密码。
- 默认 admin 密码必须经统一密码服务哈希后保存，不得继续明文写入数据库或日志。

该决定针对新数据库默认账号创建逻辑。是否删除已有数据库中已经存在的 `staff` 记录属于数据清理／迁移，需要实施时单独确认和验证。

#### 目标

新数据库只幂等创建 `admin / 123456`，密码使用统一版本化格式存储；不再创建示例员工账号，不输出默认密码日志，也不能把 `123456` 当作任何账户的认证绕过条件。

### P0-3：编辑用户会把留空密码改为 MD5 空字符串，并且失败也提示成功

#### 证据

- `lib/features/users/widgets/user_dialog.dart` 明确提示“留空则不修改密码”，但保存时把空输入转换为 `password: ''`。
- `lib/features/users/services/user_crud_service.dart` 的 `updateUser()` 无条件对 `user.password` 计算 MD5，因此会写入 `MD5("")`。
- UI 调用 `provider.updateUser(user)` 后不检查返回的 `bool`，直接显示“用户更新成功”并关闭弹窗。
- 新增用户同样不检查 `id > 0`，`-1` 也会显示为创建成功。
- 用户列表和患者删除页面还有同类“忽略返回值后提示成功”的模式。

#### 实际影响

- 仅修改头像、邮箱、角色或医生字段，也会使原密码立即失效。
- 数据库未写入时用户仍看到成功提示，造成状态认知与真实数据不一致。
- 管理员可能在不知情的情况下锁死其他账号。

#### 目标

编辑时空密码表示“不更新密码列”；只有明确输入新密码时才进入密码服务。所有 UI 必须根据返回值或异常决定成功、失败和是否关闭。

## 4. 高风险问题

### P1-1：密码存储、验证和升级规则分裂

#### 证据

- 默认账号写明文。
- `UserCrudService` 新增和更新用户使用无盐 MD5。
- `SqliteUserDataSource` 与 `MySqlUserDataSource` 新增和更新用户使用无盐 SHA-256。
- 认证入口依次接受 SHA-256、MD5 和明文，并在成功后尝试升级到 SHA-256。
- `UserAuthenticationService`、两个 DataSource 和 CRUD Service 多次记录原始密码及完整哈希。

#### 实际影响

- 同一业务行为经不同入口会生成不同密码格式。
- 无盐 MD5 和 SHA-256 可被低成本离线字典或彩虹表破解。
- 调试构建和调试日志可能泄露原始密码。
- 未来继续增加入口时很难保证登录、编辑和迁移行为一致。

#### 目标

建立单一密码服务，统一生成、验证、格式识别和历史升级；新密码使用带随机盐的慢哈希格式，日志不得包含明文、盐或完整哈希。

### P1-2：采购明细写入与主记录汇总不是原子操作，连接重试可能重复插入

#### 证据

- `lib/providers/purchase_provider.dart` 先新增、更新或删除采购明细，再单独读取全部明细并更新采购主记录汇总。
- 上述组合操作由 `DatabaseOperationWrapper.wrapOperation()` 包裹。
- 包装器在识别为连接错误时会重连并从头执行整个闭包，最多执行三次。
- 明细写入和主记录汇总之间没有 SQLite 或 MySQL 事务，也没有请求幂等键。

#### 可能故障序列

1. 第一次新增明细已经提交。
2. 汇总查询或主记录更新时连接中断。
3. 包装器重连后重新执行新增明细。
4. 同一业务明细被插入两次，或明细与主记录汇总短暂、永久不一致。

更新和删除也可能形成“明细已变化、主记录汇总未更新”的部分成功状态。

#### 目标

将明细变化和汇总更新放入同一数据库事务；MySQL 重试只重试未提交事务，新增操作还应具有业务幂等保护。

### P1-3：患者删除流程在 MySQL 下未实现关联处理，SQLite 下也不是事务

#### 证据

- `PatientDeletionService` 在 MySQL 模式下直接返回空预约列表，并记录“不支持直接查询预约”。
- MySQL 模式的 `_deleteAppointment()` 固定返回 `0`。
- MySQL 表外键没有统一 `ON DELETE CASCADE`。
- SQLite 模式逐条删除预约，单条失败被捕获后继续删除患者，整个过程没有事务。
- 服务只显式处理预约，没有统一处理财务、材料、病历、图片等患者关联数据。
- 患者列表页面忽略删除返回值，返回 `0` 也提示成功。

#### 实际影响

- MySQL 中有关联数据的患者可能始终无法删除。
- SQLite 可能只删除一部分关联记录，或因外键配置差异留下孤儿数据。
- UI 可能显示删除成功，但患者仍然存在。

#### 目标

先明确业务删除策略：禁止删除并列出关联、事务级联删除，或软删除。SQLite 与 MySQL 必须采用相同业务语义，并返回可验证的结果。

### P1-4：数据库配置异常时静默删除配置并自动回退 SQLite

#### 证据

`lib/utils/config_utils.dart` 在配置解密、读取或 JSON 解析失败后直接删除 `database_settings.json`，外层再吞掉异常并返回默认 SQLite 配置。

#### 实际影响

- 临时读取错误、密钥损坏或文件部分写入都可能导致原配置被不可恢复地删除。
- 用户重启后进入另一套 SQLite 数据库，表现为“数据全部消失”。
- 没有明确提示当前发生了数据源降级，也没有提供原配置恢复入口。

#### 目标

配置写入使用临时文件和原子替换；读取失败时保留原文件，记录可理解的错误并阻止静默切换。只有用户明确确认后才能重建或切换数据源。

## 5. 中风险与系统性规范问题

### P2-1：`SyncConfig.syncTables` 被保存但执行时完全忽略

- `SyncConfig` 默认和持久化 `syncTables`。
- `SyncManager` 实际固定遍历 `SyncTableConfig.syncTableNames`。
- 两份默认表清单不同；实际执行额外包含 `users`、`appointments`、`materials` 和 `material_images`。
- 同步对目标 SQLite 表采用先清空再插入，因此被意外纳入的表会被整表覆盖。

目标：保留唯一同步表配置源；执行前校验表集合、依赖顺序和外键关系，并在日志中记录实际同步范围。

### P2-2：会话身份同时保存在 `AppState` 和 `UserProvider`

- 登录成功后同时写入 `UserProvider.currentUser` 与 `AppState.currentUser`。
- 设置页退出登录只调用 `AppState.logout()`，未调用 `UserProvider.logout()`。
- 财务、采购、预约和患者表单的权限或医生默认值主要读取 `UserProvider.currentUser`。

影响：退出登录后 Provider 仍持有旧用户和权限缓存，形成双数据源和过期身份风险。目标是只保留一个会话真源，并让登录、退出、数据库切换和权限缓存失效走同一入口。

### P2-3：原生权限与网络策略范围过大

- Manifest 申请 `MANAGE_EXTERNAL_STORAGE`，并通过 `tools:ignore="ScopedStorage"` 绕过提示。
- 同时保留旧式 `READ_EXTERNAL_STORAGE`、`WRITE_EXTERNAL_STORAGE`。
- 文件导出多处硬编码 `/storage/emulated/0/Download`。
- `android:usesCleartextTraffic="true"` 与网络配置对所有域名开放明文通信。

处置决定：当前受控局域网场景不整改本项；若未来应用商店发布、目标 Android 版本导致权限失败或扩大网络范围，再单独复审。

### P2-4：硬编码和大文件问题已经系统化

整改状态（2026-07-20）：批次 7 已完成；主人确认按现有自动验证收口。新建 SQLite 患者表不再写入固定医生默认值；新增患者会以当前用户已配置的医生姓名作为默认值。角色、模块权限键、数据库默认值和下载目录已收口到单一代码入口；本轮涉及页面的重复导航色、圆角和间距已复用主题 token。未进行全仓颜色替换或大文件拆分。

定向统计结果：

- 272 个 Dart 文件中有 121 个非主题文件直接使用 `Colors.*` 或 `Color(0x...)`。
- 非主题代码中约有 1383 处直接颜色引用。
- 最大 Widget／Screen／Service 文件多处超过 700 行，最高超过 1100 行。
- 审核时 SQLite 患者表默认医生硬编码为具体姓名“申向歌”（已于批次 7 移除）。
- 默认数据库名、root 用户、端口、下载目录和 UI 视觉值分散在多个文件中。

颜色统计包含白色、透明色和明确语义色，不应机械批量替换；但当前规模已经明显违反项目主题 token 和统一配置入口规范。整改应从本轮修改涉及的页面和高频公共组件开始，不做一次性全仓格式化或大重构。

## 6. 已确认的正向基础

- 当前 Flutter analyzer 基线通过。
- 多数 SQL 查询使用参数绑定，未在本轮确认直接的用户输入 SQL 注入。
- 项目已有 `MapParser`，多个模型已经使用集中解析工具。
- SQLite 同步过程已经使用事务，说明项目具备事务实现基础。
- “记住密码”保留现有本地应用存储方式，不引入额外凭证服务或复杂迁移。
- 近期已经完成无用代码与重复实现治理，当前主要矛盾已从死代码转为现用逻辑正确性和边界一致性。

## 7. 整改优先级

建议按以下顺序实施，详细步骤见同目录《Android 端代码审核整改执行方案》：

1. 冻结基线并建立认证、权限和复合写入回归测试。
2. 统一密码服务，修复空密码更新和结果误报。
3. 收紧模块、用户管理和数据查询权限。
4. 将默认账号收口为唯一的 `admin / 123456`，并统一会话真源。
5. 修复采购事务和患者删除策略。
6. 修复配置持久化和同步范围。
7. 以增量方式治理主题、常量和大文件，不与高风险逻辑修复混做。

## 8. 审核限制

- 本轮没有连接真实 MySQL 实例，也没有执行 SQLite／MySQL 数据写入回归。
- 没有在真机验证文件权限、配置损坏、前后台重连和患者删除。
- 没有进行渗透测试、APK 逆向或数据库网络暴露检查。
- 颜色和大文件统计只用于判断系统性程度，不代表每一处直接颜色都是缺陷。
- 权限可见范围最终需要产品确认；在确认前，应按医疗和财务数据的最小权限原则设计，不能继续默认全量放行。
