# Windows 端代码审核整改执行方案

方案日期：2026-07-19。

状态：整改实施中；进度 1～5 已完成；进度 3 按主人决定保留本地明文凭证记忆；主人确认阶段 1～5 按自动验证完成。

本文记录 Windows 端第二轮代码审核发现的认证安全、财务权限、异步加载和明显冗余问题，并给出可由后续任意模型直接执行的分批整改步骤。本文是实施依据，不代表问题已经修复。

## 1. 目标与成功标准

### 1.1 目标

1. 消除固定通用密码登录任意账户的认证绕过。
2. 统一密码生成、验证和兼容升级规则，保证新安装默认管理员仍可使用 `admin / 123456` 首次登录。
3. 保留本地“记住用户名密码”功能，并明确其明文存储风险。
4. 确保财务患者聚合、收费明细、计数、分页和统计始终使用同一医生权限边界。
5. 修复采购搜索的并发覆盖和页面销毁后 `setState` 风险。
6. 清理由现用代码路径确认无消费者的旧分页链、重复委托和重复通知。

### 1.2 最终成功标准

- 只有账户自身密码能够登录该账户；`admin`、`123456` 不再是任意账户的通用密码。
- 新数据库自动创建默认管理员，`admin / 123456` 能够首次登录。
- 通过用户管理界面新增或修改密码后，可以使用所设置的密码登录。
- 旧数据库中的 MD5、SHA-256 或历史明文密码仍可按明确兼容规则登录，并在成功登录后升级为统一格式。
- 勾选“记住密码”后，用户名和密码继续通过本地偏好保存并自动回填；该行为由主人于 2026-07-19 明确保留。
- 非管理员只能看到其医生身份对应患者的财务数据，且列表、分页总数和统计口径一致。
- 快速输入采购搜索词时，旧请求不能覆盖新请求；离开页面后没有 `setState() called after dispose()`。
- 规定的自动测试和静态检查全部通过；SQLite 与 MySQL 人工回归完成后才能把事项标记为已完成。

## 3. 问题清单与证据

### P0-1：固定通用密码绕过账户认证

证据：

- `lib/screens/login_screen.dart` 的 SQLite 登录分支直接接受 `password == 'admin'` 或 `password == '123456'`。
- 同文件的 MySQL 登录分支具有相同逻辑。
- 代码先按用户名查找账户，再执行上述判断，因此任何已存在账户都可被固定密码登录。

影响：账户隔离完全失效；如果知道管理员用户名，可直接取得管理员身份。

目标行为：默认密码只对密码确实为 `123456` 的默认管理员有效，不能登录其他账户。

### P0-2：密码算法分叉导致真实密码不可用

证据：

- 登录页和默认管理员初始化使用 MD5。
- `UserProvider.addUser`、`UserProvider.updateUser` 使用 SHA-256。
- `UserProvider.registerUser`、`UserProvider.updateUserPassword` 又使用 MD5。
- `UserValidationService.hashPassword` 使用 SHA-256。
- 登录页只计算 MD5，同时允许明文与存储值直接比较。

影响：通过现用用户表单创建的 SHA-256 用户不能用原始密码正常登录；当前通用密码绕过掩盖了该缺陷。

目标行为：所有写入入口使用同一版本化密码格式；验证入口集中到一个服务；历史格式只在兼容验证中出现。

### P0-3：登录凭证以明文写入本地偏好

证据：`lib/features/users/helpers/credential_storage_helper.dart` 将用户名和原始密码分别写入 `saved_username`、`saved_password`。

影响：能够读取应用偏好文件的本机用户或程序可直接取得登录密码。

整改决定：主人于 2026-07-19 明确要求不使用 Windows Credential Manager，保留现有本地存储方式的“记住用户名密码”。因此本项不再作为安全整改目标；`saved_password` 将继续保存明文，风险为能读取应用偏好文件的本机用户或程序可直接取得登录密码。

### P0-4：财务数据权限过滤不完整

证据：

- `FinancialQueryService.getPatientAggregatesPage` 没有向数据源传递 `doctorFilter`。
- `getFinancialItemsCount` 和 `getFinancialItemsWithDetails` 没有传递 `doctorFilter`。
- 只有 `getAllFinancialItemsWithDetailsFiltered` 传递了医生过滤条件。
- 财务管理页面没有搜索词时把 `patientIds` 保持为 `null`，不能依靠患者搜索结果形成权限边界。
- `FinancialPermissionService` 在 `UserProvider` 或当前用户为空时返回“不限制”。

影响：非管理员可能读到其他医生患者的财务明细、聚合金额或分页总数；统计与列表还可能使用不同权限口径。

目标行为：权限条件在数据库查询层统一生效；身份缺失或权限解析失败时必须失败关闭，返回空结果或明确错误，不能返回全量数据。

### P1-1：采购搜索存在请求竞态

证据：`PurchaseRecordsScreen` 的搜索输入每次变化都会立即调用 `_loadData`；一次加载串行执行计数、全量统计和分页查询，没有 debounce、请求编号或过期结果丢弃。

影响：快速输入时会产生大量数据库查询；早发请求可能晚返回并覆盖最新搜索结果。

目标行为：输入停止短暂时间后才查询；只有最后一次请求能够写入页面状态。

### P1-2：异步结束后可能在已销毁页面调用 `setState`

证据：`PurchaseRecordsScreen._loadData`、`MaterialsScreen._loadData` 在 `await` 后直接 `setState`，成功和异常路径均未完整检查 `mounted`。

影响：加载期间离开页面可能触发 Flutter 生命周期异常。

目标行为：每次跨越 `await` 后，在读取 `context` 或写页面状态前检查 `mounted`；过期请求不更新状态。

### P1-3：登录页面重复承担数据库与认证职责

证据：登录页面同时负责建表、创建默认管理员、密码哈希、SQLite/MySQL 查询、凭证保存、状态设置和导航。项目已经存在用户数据源、schema 与数据库初始化服务。

现有登录页兜底建表逻辑还包含两个明确错误：

- SQLite `CREATE TABLE users` 最后一个字段后保留逗号。
- MySQL 表定义使用 `created_at`，插入默认管理员时使用 `createdAt`。

目标行为：登录页只负责表单、调用认证服务和导航；schema 与默认用户初始化统一留在数据库初始化入口。

### P2：明显冗余候选

以下候选必须在实施当日重新执行 `rg`，确认没有新增消费者后才能删除：

1. 预约旧分页链：`AppointmentProvider.getPaginatedAppointments`、`getAppointmentsCount`、`getAppointmentStatistics`，以及接口和 SQLite/MySQL 对应实现。现行预约页面使用 `AppointmentStateService` 的列表状态与内存分页。
2. 财务旧分页链：`FinancialProvider.getFinancialRecordsCount`、`getFinancialRecords`，以及其接口和 SQLite/MySQL 对应实现。
3. 财务重复委托：`FinancialProvider.getFinancialItems` 与 `getFinancialItemsByRecordId` 语义相同；前者只剩患者详情加载服务调用。
4. 采购重复通知：数据变更后先调用 `clearCache()`，随后又调用 `markPurchasesNeedRefresh()`；前者已经设置刷新标志并安排通知。
5. 空 `else {}`、无信息日志和刚设置状态后再次验证并重复设置的防御性代码。

删除文件或删除整条 API 链属于红线操作，执行前必须向主人说明目标和影响并取得确认。

## 6. 批次 1：统一密码生成与验证

### 6.1 设计决策

推荐使用现有 `crypto` 依赖实现版本化 PBKDF2-HMAC-SHA256，不新增依赖。存储格式必须能够自描述，例如：

```text
pbkdf2_sha256$<iterations>$<base64_salt>$<base64_hash>
```

具体迭代次数集中定义在密码服务中，不散落在 UI、Provider 或数据源。盐使用 `Random.secure()` 生成，每个密码独立。

兼容验证顺序：

1. 新格式：按版本、迭代次数和盐验证。
2. 64 位十六进制：按历史 SHA-256 验证。
3. 32 位十六进制：按历史 MD5 验证。
4. 其他历史值：仅为明确存在的明文旧数据执行一次常量时间比较。
5. 绝不再把 `admin` 或 `123456` 当通用通过条件。

历史格式验证成功后立即生成新格式并更新当前用户密码，实现渐进升级。升级失败时本次登录是否继续，应采用“登录成功但记录错误并下次重试”，避免旧账户因迁移写入故障被锁死；不得把原始密码写入日志。

### 6.2 测试先行

新增密码服务单元测试，至少覆盖：

- 同一明文两次生成的哈希不同，但都能验证成功。
- 错误密码验证失败。
- 历史 MD5 正确密码通过，错误密码失败，并标记为需要升级。
- 历史 SHA-256 正确密码通过，错误密码失败，并标记为需要升级。
- 明文旧值只匹配自身，不匹配其他值，并标记为需要升级。
- `123456` 不能验证密码不是 `123456` 的账户。
- 畸形版本串、非法 Base64、非法迭代次数安全返回失败，不能抛出未处理异常。

### 6.3 实施步骤

1. 在用户功能目录新增单一密码服务或 helper；命名应匹配现有项目风格。
2. 把 `UserProvider.addUser`、`updateUser`、`registerUser`、`updateUserPassword` 的哈希生成统一改为调用该服务。
3. 把默认管理员创建改为调用同一服务。
4. 删除业务代码中重复的 MD5/SHA-256 helper 和由删除产生的孤儿 import。
5. 登录验证只调用认证 service；不得继续在 Widget 内直接判断哈希。
6. 认证成功且需要升级时，通过用户数据源按用户 ID 更新密码字段。
7. 日志只记录“密码格式已升级”或错误类型，禁止记录明文、盐、完整哈希。

### 6.4 验收

- 新增用户、编辑用户密码、重置密码、默认管理员四条写入路径生成同一版本格式。
- 旧 MD5、SHA-256 和明确的明文历史账户可以使用原密码登录一次并完成升级。
- 任意账户都不能被固定通用密码绕过。

### 6.5 实施记录

- 2026-07-19：新增 `lib/features/users/services/password_service.dart`，使用现有 `crypto` 依赖实现 PBKDF2-HMAC-SHA256 版本化存储、随机盐和常量时间比较；兼容验证历史 SHA-256、MD5 与明确的明文密码，验证结果会标记是否需要升级。
- 2026-07-19：`UserProvider.addUser`、`updateUser`、`registerUser`、`updateUserPassword` 已统一改为调用该服务；移除 `UserValidationService` 中无消费者的 SHA-256 生成入口及 Provider 中会输出完整哈希的日志。
- 2026-07-19：扩展 `test/features/users/services/user_validation_service_test.dart` 的密码覆盖，并新增认证服务测试；认证相关定向测试 14 项通过，`cmd.exe /c flutter analyze --no-pub` 为 `No issues found!`。登录认证、默认管理员和成功登录后的密码升级写回已接入，SQLite/MySQL 人工回归尚未执行。

## 9. 批次 4：财务权限查询一致性

### 9.1 设计原则

权限必须在数据库查询层生效，不能先分页再在 Dart 中过滤。计数、分页记录和统计必须复用同一查询条件构建逻辑。

用户状态规则：

- 管理员：`doctorFilter = null`，可查看全部。
- 非管理员且医生字段有效：`doctorFilter = currentUser.doctor`。
- 用户为空、Provider 未就绪、医生字段为空或解析异常：失败关闭，返回明确的“无访问主体”结果，不能等价于管理员。

建议不要继续使用 `__NO_DOCTOR__` 魔法字符串；优先建立明确的权限查询结果类型或在 service 层返回空结果。如果为控制改动范围继续使用哨兵值，必须集中为语义常量并有测试。

### 9.2 接口改动

为以下接口一次性增加 `doctorFilter`，并同时修改抽象接口、SQLite、MySQL、QueryService 和 Provider 调用：

- `getPatientAggregatesPage`
- `getFinancialItemsCount`
- `getFinancialItemsWithDetails`

`getAllFinancialItemsWithDetailsFiltered` 已有该参数，应与前三者共用相同条件构建规则。

### 9.3 SQL 实施要求

1. 患者聚合查询已经连接 `patients p`，添加 `p.doctor = ?` 条件。
2. 收费项计数和分页查询在启用医生过滤时必须连接 `financial_records fr` 与 `patients p`。
3. 计数 SQL 与列表 SQL必须由同一条件构建器生成，参数顺序完全一致。
4. SQLite 与 MySQL 的字段、空值、日期边界、患者 ID 列表和医生条件逐字段对齐。
5. 不允许先取全量数据或一页数据后在 Dart 中逐患者查询过滤，避免数据泄漏、N+1 查询和分页总数失真。

### 9.4 测试先行

至少覆盖以下数据集：医生甲患者、医生乙患者、无医生患者、各自多条财务记录和收费项。

测试断言：

- 管理员计数、分页、患者聚合和统计包含全部数据。
- 医生甲只得到医生甲患者的数据；医生乙同理。
- 用户为空或医生字段为空时返回空结果。
- 同一条件下 `count == 所有分页结果条数之和`。
- 搜索、日期范围、金额范围和医生过滤组合后，计数与列表一致。
- SQLite 与 MySQL 对同一测试数据返回相同业务结果；MySQL 无法在单元测试运行时，至少对 QueryService 参数透传做 fake 测试，并安排真实 MySQL 人工回归。

### 9.5 页面回归

- 管理员切换“按患者／按收费记录”显示，金额、总数和分页正常。
- 非管理员只能看到自己的患者，两种显示模式和统计弹窗一致。
- 搜索不存在的患者返回空列表，不回退全量。
- 登录用户切换或权限刷新后，财务缓存和页面立即失效并重新按新权限加载。

### 9.6 实施记录

## 10. 批次 5：采购搜索竞态与生命周期

### 10.1 实施步骤

1. 为采购搜索增加 `Timer` debounce，建议 300～400 ms，值集中为页面语义常量。
2. 增加递增请求编号，例如 `_loadGeneration`。
3. `_loadData` 开始时捕获当前搜索词、页码和请求编号，整次查询只使用这些快照。
4. 每次 `await` 后检查 `mounted`；写状态前同时确认请求编号仍是最新。
5. 过期请求直接返回，不写列表、统计、错误或 loading 状态。
6. `dispose` 中取消 debounce Timer，并使当前请求编号失效。
7. `_loadStatistics` 接收捕获的搜索词参数，不直接读取可能已变化的 `_searchQuery`。
8. 为 `MaterialsScreen._loadData` 的成功和异常路径补齐 `mounted` 检查；不借机重构材料筛选逻辑。

### 10.2 测试

- 连续输入 `a`、`ab`、`abc` 时只执行最终查询，或只有最终请求能更新状态。
- 模拟 `a` 请求晚于 `abc` 返回，页面仍显示 `abc` 结果。
- 查询中销毁页面不抛生命周期异常。
- 清空搜索后页码回到第一页，统计与列表使用空搜索条件。
- 数据库异常只由最新请求显示错误，旧请求异常不能覆盖新结果。

### 10.3 实施记录

- 2026-07-19：采购页搜索改为 350ms 防抖；每次输入立即递增请求世代，使已经运行的旧请求不能写回页面。加载过程使用搜索词和页码快照，计数、统计与分页查询均使用同一搜索词；每次异步返回及异常写状态前校验 `mounted` 和请求世代。
- 2026-07-19：采购页销毁时取消防抖计时器并使现有请求失效；材料页 `_loadData` 在异步读取材料后以及异常写状态前检查 `mounted`。`cmd.exe /c flutter analyze --no-pub` 为 `No issues found!`；当前测试结构没有可注入的页面异步数据源，未新增脱离实际页面生命周期的伪回归测试。主人确认按自动验证完成。
