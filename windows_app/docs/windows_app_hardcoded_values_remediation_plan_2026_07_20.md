# Windows 端硬编码治理实施方案

方案日期：2026-07-20。

状态：部分实施。复查确认批次 6～8 尚有 HC-08、HC-09、HC-11、HC-12 残留，后续按补充整改方案继续实施；本文仍作为总体进度入口。

## 1. 目标与成功标准

### 1.1 目标

1. 环境路径、应用配置、角色权限、模块标识和数据库连接策略只在统一入口定义。
2. 公共 UI 组件只使用 `Theme.of(context)`、`context.tokens` 或统一医学语义色，不绕过五套 Windows 主题。
3. “获取全部”、患者归属、预约状态等业务语义不再依赖魔法数字或多套字符串映射。
4. 保留协议固定值、算法常量和局部布局尺寸等合理字面量，不进行机械式常量抽取。
5. 每个批次有独立测试和退出条件，不把路径、权限、主题和查询行为混成一次高风险改动。

### 1.2 最终成功标准

- Windows 业务源码不包含开发者个人绝对路径。
- 日志不输出默认密码或其他凭证。
- 新增患者显式使用当前用户配置的医生姓名；新建 SQLite schema 不包含固定医生默认值。
- 可创建角色、角色显示和权限矩阵来自同一份定义，不再出现 UI 与权限服务角色集合分叉。
- 统计和导出不再使用 `5000`、`999999` 模拟全量查询。
- 公共提示、日期选择、连接警告和加载组件能随当前主题变化。
- 可配置应用名称在主界面、关于页、导出和日志中口径一致。
- 数据源、模块、预约状态、MySQL 默认端口和数据库时间格式均有明确唯一入口。
- `flutter analyze --no-pub`、相关专项测试和全量测试通过；规定的人工回归完成前保持“待人工回归”。

## 2. 已确认边界

### 2.1 明确保留

1. 登录页继续预填 `admin / 123456`。
2. 保留“记住用户名密码”以及重启后自动回填用户名和密码的行为。
3. 不增加首次登录强制改密状态。
4. 保留新数据库默认管理员首次登录规则；本方案只移除日志中的明文密码，不改变认证行为。
5. 既有 SQLite 数据库不执行患者表 schema 迁移，不修改其中任何内容；只修正新建数据库 schema 和应用写入行为。
6. 不修改 Android 端。

### 2.2 不视为问题的合理字面量

- `AppThemeTokens` 和 `MedicalSemanticColors` 内集中定义的主题／医学语义色。
- PDF、Excel 等独立输出媒介内部的版式和打印颜色。
- 局部 `padding`、圆角、字号、控件尺寸和动画时长。
- SQL 表名、列名、协议关键字以及 schema 定义中的类型长度。
- `3306` 作为 MySQL 协议默认端口这一业务值本身；问题是目前存在多份默认和回退逻辑。
- 不同页面用于展示的日期格式；本方案只统一数据库持久化格式。

## 7. 批次 2：环境路径与敏感日志

### 7.1 移除开发者绝对路径

目标文件：`lib/utils/app_paths.dart`。

实施：

1. 删除两个 `D:\Data\...\windows_app\tools` 候选路径。
2. 保留正式环境的 `AppPaths.appDirectory/tools`。
3. 开发环境只使用工作目录或项目目录推导出的相对 `tools` 路径，不写任何用户名、盘符或仓库绝对位置。
4. 每个候选仍需同时存在 `mysql.exe` 和 `mysqldump.exe` 才视为有效。
5. 找不到工具时继续返回正式默认位置并记录不包含个人路径的提示。

测试：覆盖正式目录命中、相对开发目录命中、目录存在但工具不完整、全部缺失四种情况。若现有静态 getter 不便测试，只做最小可注入的候选构建函数，不引入配置框架。

### 7.2 清理默认密码日志

目标文件：`lib/services/sqlite_database_service.dart`。

将“成功创建默认管理员用户: admin/123456”改为不包含密码的成功日志。不得因此修改：

- `login_screen.dart` 的初始用户名和密码预填。
- `credential_storage_helper.dart` 的保存与回填行为。
- 默认管理员密码生成、认证或首次登录规则。

退出条件：业务日志中不再出现 `admin/123456`，登录行为没有变化。

## 8. 批次 3：角色与权限定义统一

### 8.1 已确认分叉

- 用户管理 UI 可创建：`admin`、`doctor`、`assistant`、`receptionist`。
- `User.roleDisplay` 维护相同四个显示值。
- `UserProvider.hasPermission` 却使用 `nurse`、`accountant`、`inventory_manager`，且没有为 `assistant` 建立明确权限。

这会导致可创建角色与权限判断不一致，属于业务权限问题，不能只做字符串替换。

### 8.2 推荐方案

以当前用户管理 UI 的四个角色作为现阶段可创建角色：

- `admin`
- `doctor`
- `assistant`
- `receptionist`

集中定义每个角色的稳定存储值、显示名、图标和默认模块权限。`User`、用户表单、角色选择器、用户卡片和权限服务统一读取该定义。

实施前仍需主人确认 `assistant` 对患者、预约、财务、材料和采购的权限矩阵。未确认前，本批只能整理证据和测试，不能猜测权限。

对数据库中可能已经存在的 `nurse`、`accountant`、`inventory_manager`：先只做读取统计，不修改数据。若需要改写历史角色值，属于数据迁移，必须另行确认。

### 8.3 测试

1. 每个可创建角色都有显示信息和权限定义。
2. 管理员保留全部权限。
3. 未知或缺失角色失败关闭。
4. 用户表单选项、角色卡片和 Provider 权限集合一致。
5. 旧角色值按最终确认的兼容策略处理，不静默提升权限。

## 9. 批次 4：移除全量查询魔法数字

目标位置：

- `lib/screens/patients_screen.dart` 的 `pageSize: 999999`。
- `lib/features/patients/widgets/patient_export_dialog.dart` 的 `pageSize: 5000`。

推荐使用患者查询服务提供共享的分批全量读取能力：

1. 使用语义明确的内部批大小，例如集中定义的 `exportBatchSize`，不把它当作“全部”的上限。
2. 按总数／总页数循环读取，直到没有下一页。
3. 每批继续使用现有搜索、日期、排序和医生权限条件。
4. 统计与导出复用同一读取编排，避免一处修复另一处继续截断。
5. 导出超过 5000 条时不能静默丢失；中途失败必须报告失败，不能输出不完整文件并提示成功。

测试至少模拟多批数据、最后一批不足、空结果、第二批失败和权限过滤，证明结果不受 5000 或 999999 限制。

## 10. 批次 5：公共组件主题治理

### 10.1 固定 Material 色板

目标组件：

- `lib/widgets/success_toast.dart`
- `lib/widgets/modern_date_picker.dart`
- `lib/widgets/mysql_connection_warning.dart`
- `lib/widgets/loading_indicator.dart`

实施规则：

1. 成功、警告、错误、信息及容器色分别使用 `context.tokens` 对应语义 token。
2. 文本、边框、背景、遮罩和禁用态使用 `Theme.of(context).colorScheme` 或 token，不直接使用蓝／红／橙／灰色板。
3. 公共组件内部读取主题，不要求调用方传固定品牌色。
4. 保留 `Colors.transparent` 等无主题语义的透明值。

### 10.2 平行颜色体系

`widgets/dental_icons.dart` 中的 `DentalColors` 同时包含主题色、状态色、性别颜色和牙科语义色。治理时：

1. 主题色和状态色迁移到当前主题 token。
2. 性别和牙科业务识别色复用 `MedicalSemanticColors`。
3. 图标数据与可复用 Widget 保留，不借机重写整个文件。
4. `unified_search_field.dart` 的错误色不再从 `DentalColors` 获取。

### 10.3 主题色卡

`features/settings/widgets/theme_section.dart` 的预览色卡应从 `WindowsThemeVariant.tokens` 派生，避免与 `AppThemeTokens` 重复维护同一组色值。

验证五套主题下的成功／错误提示、删除确认、MySQL 警告、日期选择、加载状态和主题选择页。

## 11. 批次 6：应用名称唯一真源

现有 `SettingsProvider.appName` 已支持配置，但启动标题、单实例提示、采购导出、日志导出、关于页版权等仍写死默认名称。

实施：

1. 集中定义唯一的默认应用名称，仅用于配置缺失和 Provider 初始化前的回退。
2. 已经能够访问 `SettingsProvider` 的页面全部使用 `settingsProvider.appName`。
3. `PurchaseExportService` 等无 BuildContext 服务通过参数接收当前应用名称，不读取隐式全局状态。
4. `LogManager` 的导出头通过调用参数或明确的应用配置入口获得名称。
5. 示例／提示文案可以展示默认名称，但应复用同一默认常量。

测试修改应用名称后主页、登录页、关于页、采购导出和日志导出均使用新名称；应用初始化失败等早期界面使用统一默认名称。

## 12. 批次 7：数据源与模块标识收口

本批范围较大，必须只收口状态决策点，不机械替换 SQL 表名和 Map 字段名。

### 12.1 数据源标识

建立带稳定存储值和安全解析的类型，覆盖：

- `sqlite`
- `mysql`
- `global`
- `modular`

Provider、设置服务和数据源初始化内部使用类型；写入 SharedPreferences／JSON／Map 时显式转换为稳定字符串。未知值按现有安全策略回退或失败关闭，不通过宽泛默认掩盖配置损坏。

### 12.2 模块标识

集中定义 Dashboard、患者、预约、财务、材料、采购、病历、用户和设置模块 ID。主页导航、用户模块权限、模块数据源和连接警告复用同一集合。

特别核对 `medical_records`、`medical` 以及“病历跟随 patients 数据源”的现有语义，不能仅因名称相似直接合并。

测试配置序列化兼容、模块集合完整、未知值处理、模块权限和模块数据源选择。

## 13. 批次 8：时间、连接策略与预约状态

### 13.1 数据库时间格式

持久化层统一使用现有 `DateTimeFormatter.toDbString`、`fromDbString` 和 `nowDbString`。SQLite／MySQL 预约数据源、数据库结构日志和数据库初始化不再各自创建 `DateFormat('yyyy-MM-dd HH:mm:ss')`。

页面展示、文件名和日志展示格式不在本项强制统一。

### 13.2 MySQL 默认值与超时

集中定义：

- 默认端口 `3306`。
- 建连超时。
- 连接验证超时。
- 用户主动测试连接超时。
- 健康检查间隔。

不同语义可以使用不同数值，但必须有不同名称，不能用一个“全局超时”掩盖业务差异。设置界面、Provider、备份服务和连接服务复用同一默认端口。

### 13.3 预约状态

集中维护 `scheduled`、`completed`、`cancelled`、`missed` 与中文显示名。模型解析、Dashboard 颜色、预约卡片选项和详情页按钮复用同一入口，并兼容现有中英文存储值；本轮不迁移历史数据库状态。
